gitFlow / Branch Strategy

⎇ Git Branching Strategy

The agreed team structure for all code changes — GitFlow model

Branch Purpose Source From Merge Into Direct Push Lifetime
main Production-ready code only — — NEVER Permanent
develop Integration branch for all features main main (via release) NEVER Permanent
feature/* Individual feature / user story develop develop YES Sprint duration
release/* Release stabilization & bugfixes develop main + develop NEVER Until deploy
hotfix/* Critical production fix main main + develop YES Until merged
✅ Correct Naming
# Feature branches feature/PROJ-123-user-auth-login feature/PROJ-456-payment-integration feature/PROJ-789-dark-mode-ui # Bugfix branches bugfix/PROJ-321-fix-null-pointer # Release branches release/1.4.0 release/2.0.0-beta # Hotfix branches hotfix/PROJ-999-critical-auth-bypass
❌ Incorrect Naming
# ❌ No ticket reference feature/my-feature # ❌ PascalCase / spaces Feature/UserAuth feature/user auth # ❌ Too vague feature/fix feature/updates # ❌ Direct on protected main ← push blocked develop ← push blocked
📐 Naming Pattern
pattern: <type>/<TICKET-ID>-<short-kebab-description> types: feature | bugfix | hotfix | release | chore | refactor ticket: JIRA/Linear ticket reference (mandatory) desc: lowercase, hyphen-separated, max 5 words example: feature/PROJ-101-add-oauth-google

gitFlow / Workflow

⟳ End-to-End Workflow

From user story to production — the complete agile journey

📦 Commit Message Convention
# Format: <type>(<scope>): <description> # # Types: feat — new feature fix — bug fix docs — documentation only style — formatting, no logic change refactor — code restructure test — add or update tests chore — build, deps, tooling ci — CI/CD configuration # Examples: "feat(auth): add JWT refresh token rotation" "fix(cart): resolve race condition on checkout" "docs(readme): update env setup instructions" "chore(deps): bump lodash to 4.17.21"
📝 Pull Request Checklist
  • ✓Branch named per convention (type/TICKET-desc)
  • ✓All commits follow conventional format
  • ✓Unit tests written and passing locally
  • ✓CI/CD pipeline passing (green checks)
  • ✓No merge conflicts with target branch
  • ✓PR description filled with context + ticket link
  • ✓At least 2 reviewers assigned
  • ✓Screenshot/video for UI changes
  • →Self-review done before requesting review
📐 Sprint Workflow Phases
1. Ticket Created
User story in backlog → sprint planned, branch name determined
2. Branch Created
feature/PROJ-ID-desc from develop HEAD
3. Development + Daily Sync
Code, commit (conventional), rebase daily
4. PR Opened → Review
2 approvals, CI green → merge to develop
5. Release Cut
release/X.Y.Z from develop → QA testing
6. Production Deploy
Merge release → main, tag vX.Y.Z
🚨 Hotfix Emergency Procedure
🚨Only for P0 production incidents. Requires on-call lead approval.
# 1. Branch from main (NOT develop!) git checkout main && git pull git checkout -b hotfix/PROJ-999-description # 2. Fix, test, commit git commit -m "fix(critical): resolve auth bypass vulnerability" # 3. PR → main (expedited: 1 reviewer OK) # 4. After merge to main, also merge to develop git checkout develop git merge --no-ff hotfix/PROJ-999-description # 5. Tag the fix on main git tag -a v1.3.1 -m "Hotfix: auth bypass patch" git push origin v1.3.1

gitFlow / Social Contract

✦ The Social Contract

Our shared commitments as an agile engineering team

✦
This document is our living agreement. All team members have reviewed, discussed, and committed to these principles. Updated in retrospectives.
🤝 Our Core Commitments
  • 1We protect main. main is sacred — it is always deployable. No exceptions.
  • 2We use PRs for everything. No direct pushes to shared branches. Every change has a review trail.
  • 3We write meaningful commits. Conventional commits are mandatory. No "WIP", "fix", "asdf".
  • 4We review within 24 hours. PRs should not block team momentum. We prioritize review.
  • 5We sync daily. Rebase feature branches on develop every morning to minimize conflicts.
  • 6We delete merged branches. Clean repo hygiene. Feature branches die after merge.
  • 7We never force push shared branches. Force push is allowed only on your own unreviewed feature branch.
  • 8We escalate blockers. Stuck > 2 hours? Raise it in standup. We unblock each other.
⚖️ Consequences & Handling
When a contract rule is violated, we follow a blameless, learning-first approach:
1st
Discussion — Async message, understand what happened
2nd
Retro Item — Discuss in sprint retrospective, add to learnings
3rd
Process Review — Update tooling/automation to prevent recurrence
